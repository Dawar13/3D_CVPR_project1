1. Background: what these models do, and what a "hint" is

Models like MapAnything and OmniVGGT take a handful of photos of a scene and, in one pass, output a 3D reconstruction: where each camera was, and how far away every pixel is. Their selling point is that they can also take hints: where the cameras were (poses), the lens settings (intrinsics) and depth maps. With correct hints, they get much better.

The catch: in the real world hints come from GPS, phone tracking, cheap depth sensors, AI depth estimators or wrong photo metadata, so they are often wrong. Our project asks what happens then.

How we score. Rotation error = how wrong the camera directions are (degrees, between pairs of cameras). Shape error = how far the 3D points are from the truth after one overall size correction (% of distance). Real-size error = the same without the size correction. Absorption = how much of a hint's error ends up in the output (1 = copied, 0 = ignored). AUROC = how well the model's own confidence ranks bad cameras below good ones (0.5 = guessing, 1 = perfect).

2. Where E1 left us, and why E2 was needed

Experiment 1 (preregistered, run once on 10 test scenes) answered the first question: yes, a wrong hint can make MapAnything worse than giving it no hints at all. With one camera turned 15° wrong, its rotation error was +114% compared with photos only. The model copied the bad pose almost completely (absorption 0.95 at 15°), even though its own confidence did flag the bad camera.

But E1 left the questions that decide whether a fix is worth building open. Is this already known? Were the numbers big enough to matter, or just statistically detectable? Why does the model obey a hint it seems to know is wrong: a simple averaging step, or something deeper? Is it only MapAnything? Do real sensors produce such errors? And do existing tools already fix it? A method paper only makes sense if the answers line up, so E2 asks them one by one.

3. How we ran E2, and why it was done this way

The biggest risk in an experiment like this is fooling ourselves: running many tests, then reporting the ones that happen to look good. So E2 followed strict rules, each with a reason.

  • Preregistration. Before each main run we wrote down exactly what we would measure and what counts as a result, and froze it (git tags e2-prereg-C, e2-prereg-DEF). So that nobody can choose the tests after seeing the numbers.
  • Trial (dev) scenes vs test (eval) scenes. Code is debugged only on 3 separate trial scenes; the test scenes are used once. So that the test data never shapes the design.
  • "Statistically clear" AND "big enough". A result counts only if it survives Holm correction (which accounts for running many tests at once) and passes a practical threshold: shape ≥ 1 percentage point, real size ≥ 5 pp, rotation ≥ 0.25°, scale ≥ 5%. So that tiny, irrelevant effects never count as findings.
  • The scene is the unit. Several clips from the same scene are averaged first. So that we don't pretend to have more independent evidence than we do.
  • Every comparison is paired. The same clips, the same random corruptions, with and without the bad hint. So that differences come from the hint, not from different data.
  • One paid GPU session, no idle time. All E2 GPU work ran in one session on an NVIDIA RTX PRO 6000 (2026-11-01 15:27:19 → 2026-11-01 17:34:01 UTC), with automatic checks between each trial run and its main run, so the GPU never waited for a human.
  • A parity check against E1. The new GPU reproduced E1's runs: median differences 0.006 pp shape and 0.0017° rotation, and parallel processes gave bit-identical results. One extreme run (a 10× GPS jump) differed by 2.1 pp; you approved judging the check by its 99th percentile instead (Amendment 14).

4. E2-A: is this already known? (literature audit)

We opened every closely related paper. No paper measures our core findings on these models. The closest are Pow3R (two views only; it refuses grossly wrong hints), VPGGT (retrains OmniVGGT against drift-style pose noise; poses only; it doesn't detect which hint is bad), WorldMirror and TCO. We also collected realistic error sizes from the literature (phone tracking, compass, GPS, depth sensors, AI depth estimators), which replace E1's rough "realistic" labels. Details: reports/e2_literature.md.

5. E2-B: were E1's results real and big enough?

We checked that "copying" is genuine behaviour (the output camera comes from the network, not from passing the input through), then re-tested every E1 setting with the strict standard. 16 of 132 tests stay harmful, covering 9 of 19 error types; 7 of them at sizes that really occur (first camera wrong, one depth map scaled wrong, depth hints scaled wrong, every camera slightly turned, one camera turned wrong, all distances scaled wrong, same heading error on all). The harm sits on the bad camera itself: the pairs of good cameras barely change. Details: reports/e2_audit.md.

6. E2-C: how does MapAnything react to a bad hint?

We fed MapAnything carefully controlled bad hints on 24 clips from 10 test scenes (2026-11-01, finished 17:06 UTC; 3,232 runs) and asked twelve preregistered questions.

It copies, and it never overrides

Turn one camera's hint by an increasing amount and measure how much of that error appears in the output. A sensible model would follow small corrections and refuse absurd ones. MapAnything does the opposite of refusing: it copies 0.77 of a 1° error and 0.96 of a 30° error. The same holds for position errors. OmniVGGT copies about half of a rotation error at any size, and almost none of a position error.

It knows, but obeys

Yet MapAnything's own confidence clearly marks the bad camera (AUROC 0.93). The information needed to resist is inside the model; it just doesn't use it. OmniVGGT's confidence barely notices (AUROC 0.58).

Errors that agree are the dangerous ones

Give every camera a 5° error in random directions, and MapAnything's confidence drops to 0.28 of normal. Give every camera the same 5° error, and it only drops to 0.53. Drift behaves the same way. Errors that agree look self-consistent, so the model doesn't notice them. Real phone tracking errors are exactly this kind (section 8). OmniVGGT's confidence doesn't move at all with bad camera hints (ratio 1.00), so it gives no warning in either case.

Why it happens: not the averaging step

MapAnything rescales camera hints using their mean distance. A single crazy hint can wreck a mean but not a median, so one theory (our H2) was that the averaging step causes the damage. We swapped it for a median. Clean results didn't change (+0.0054° rotation), and the 10× GPS jump wasn't fixed (P7: -0.84 pp, not clear). The damage happens inside the network.

7. E2-D: does a second model behave the same?

A finding that holds for two differently built models is a property of the approach, not one model's quirk. OmniVGGT injects hints differently, so we gave it identical bad inputs: the same clips, and the same condition names, which means the same random corruptions (3,312 runs).

Result: under the strict test, none of the 9 harmful error types makes OmniVGGT worse than photos only. Two reasons. First, it copies less (about 60% instead of about 95%). Second, its photos-only mode is unstable: it fails badly in 2 of 10 scenes (terrains 32.6°, meadow 16.8°), so "worse than photos only" becomes too noisy to prove. With one camera turned 90°, OmniVGGT is worse than photos only in 8 of 10 scenes, but the strict test doesn't pass. It is also immune by design to wrong overall scale, because it rescales every hint.

8. E2-E: do real sensors cause the problem?

Everything so far used errors we injected on purpose. Reviewers will rightly ask whether real sensors produce them. So we used SceneFun3D: iPad recordings of real rooms with the iPad's own tracking (ARKit) poses and LiDAR depth, plus much better laser-scan ground truth. They come from the ARKitScenes validation split, which neither model trained on. We also added a hint that many cameras without LiDAR would really use: AI-estimated depth (Depth Anything V2, metric indoor model).

Data care. 18 rooms (3 trial, 15 test), 3 clips each, chosen by a fixed random rule. Only the frames we use were downloaded (~60 MB per video instead of ~650 MB). Some phones store frames turned 180°; this is detected per video and corrected, and the correction reproduces the dataset's own lens values to within 0.1 pixel. 5 portrait recordings were skipped, and 5 clips failing the ground-truth check were excluded, both by rules fixed before any model ran. One test clip turned out to have a broken ground-truth pose for one view (a 164° jump in half a second; the phone's own pose is fine). It stays in the main analysis as preregistered; leaving it out changes 0 verdicts.

How wrong are real hints?

Phone poses are good: 0.87° typical rotation error, and only 1.4% of views 5° or more off. Their errors build up along the recording (median correlation with view order 0.52), so they are drift-like and agreeing. LiDAR depth is excellent (×0.996, 1.2% typical error). AI depth is not: typically ×1.42 too far (range ×1.13–×1.85), with 42% typical error.

Do real hints help or hurt?

Real phone hints help. AI depth hurts both models, by about 10 percentage points of shape error and about 1° of rotation, and good phone poses don't cancel it out.

9. E2-F: do today's fixes already solve it?

A method paper must show the problem is not already solved. For each setting that is clearly harmful for MapAnything, we measured how much of the damage is left after each existing fix: 0 = fully fixed, 1 = no help, above 1 = the fix is worse than the damage. R0 ignores all hints; R1 drops the pose hints; R2 is E1's simple filter (drop poses that disagree with the photos-only answer); R3 drops cameras the model itself is unsure of; ORACLE cheats by dropping exactly the bad cameras.

What this says. For a single, grossly wrong camera, E1's filter is nearly perfect, but it also drops 12% of good cameras (R3: 3%). On real phone data that costs accuracy: the filter makes rotation worse by +0.19° because it throws away good real hints. For agreeing errors (drift, scale), the model's confidence is useless (R3 leaves 90–100%); only "drop all poses" helps, which also throws away the value of good poses. For bad depth, none of the preregistered fixes helps; simply dropping the depth hint would, if you knew it was bad. But phone LiDAR depth helps, so dropping depth always is not free.

What photos alone can reveal (the ceiling)

Any fix that uses only the photos can't detect an error smaller than the photos' own uncertainty. With photos and lens values only, camera directions are about 0.8° uncertain (2.0° in the worst 10%), and overall scale about 13% (52% in the worst 10%). So typical phone errors (about 1°) are invisible to photos, errors of 5° or more are visible, and AI depth's ~42% scale error is visible in most clips.

10. The decision

The E2 plan fixed the decision rule in advance. To GO to E3, at least one harmful error type must pass all four tests: (a) it hurts both models, (b) it happens with real sensors, (c) the best existing fix leaves at least half the damage, and (d) photos alone contain enough evidence to detect it.

Verdict: GO to E3, narrowed to depth hints. Two judgment calls behind it, stated openly:

  1. Test (a) for depth comes from the real AI-depth runs. The synthetic depth-scale test is "MapAnything only", because OmniVGGT rescales depth. But real AI depth also distorts the shape of the depth map, and that hurts both models.
  2. Test (c) holds by the frozen rule, but an obvious fix was missing from the list. "Drop the depth hint" (exploratory) leaves only 10–15% of the damage. It works only if you know the depth is bad; LiDAR depth helps, so dropping it always loses accuracy. The real open problem is deciding when to trust a depth hint, which is exactly E3's question.

Read strictly the other way, the outcome would be the analysis paper, which is already well supported.

11. What this means for the paper and for E3

  • Already solid (analysis paper): these models copy wrong hints instead of overriding them; MapAnything does so while its confidence knows; agreeing errors go unnoticed; the cause is inside the network, not the averaging step; real AI depth hurts both models while real phone sensors help; existing fixes only cover the easy case.
  • E3 target: decide from the photos alone, with no ground truth, whether a hint (first of all a depth hint) can be trusted, and use it only then. E3 must beat three simple policies: always use hints, never use them, and E1's filter. Agreeing pose errors are a secondary target, since nothing deployable handles them today.
  • Risks: OmniVGGT is less affected by synthetic errors; typical phone errors (~1°) are below what photos can detect; and time (CVPR submission on 16 November 2026).
