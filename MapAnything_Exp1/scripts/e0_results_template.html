MapAnything Vanilla Run

Before testing what wrong hints do to MapAnything, we checked that the plain, unmodified model runs correctly in our setup. This page shows what it built, the numbers, and what we fixed on the way.

Short answer

Yes. Vanilla MapAnything ran properly.

  • PASSIt ran with no errors and produced sensible 3D on a real scene.
  • PASSCorrect hints made it clearly better, as the MapAnything paper says they should. Camera angles got 75% more accurate and the 3D shape 58% more accurate.
  • PASSRunning it twice gives exactly the same answer, down to the last digit.

What we asked the model to do

We gave MapAnything 10 photos of one place (a delivery area at ETH Zurich, from the ETH3D dataset) and asked it to rebuild the place in 3D and work out where each photo was taken from. ETH3D also has a laser scan of the same place, so we can measure how close the model gets.

We ran it four ways:

  • Photos only. The model has to guess everything.
  • Photos + lens info. We also tell it each camera's focal length.
  • Correct hints. Photos, lens info, and the true position of every camera.
  • One wrong hint. Same as correct hints, but one camera's direction is turned 15° wrong. This previews E1; here it only checks that the corruption code works.

What the numbers say, in plain words

Correct hints help a lot

With the true camera positions, the 3D shape error fell from 4.2% to 1.7% and the camera-angle error from 0.73° to 0.18°. MapAnything is built to use hints like this, so this is the main sign that our pipeline feeds them in correctly. If we had a mistake in how camera positions are passed in, hints would have made things worse instead.

Lens info alone helps the shape, not the real-world size

Telling the model the focal length fixed the shape (4.2% to 1.7% error) but made its guess of real-world size slightly worse on this scene. That is one scene, so we only note it.

One wrong hint already hurts

Turning a single camera's hint by 15° raised the average camera-angle error to 3.0°, worse than photos only (0.73°). On this scene, one bad hint cost more than having no hints at all. This is exactly what E1 tests properly across many scenes. Here it only shows the test machinery works.

Removing the bad hint brings it back

When we dropped the wrong hint, errors went back to almost the correct-hint level (shape 1.8%, angle 0.30°). Our simple "compare with photos-only" filter found the bad camera by itself in all 3 runs. For a 15° error that is expected; harder cases come in E1.

Is the answer key right?

We grade the model against ETH3D's laser scans, so first we checked that the scans agree with themselves. We took the laser depth from photo 1, moved it into the view of the other photos using the true camera positions, and compared it with their own laser depth. If our camera handling were wrong, they would disagree by many percent.

What we fixed on the way

The laser depth was being matched to the wrong photos

ETH3D's laser depth belongs to the original photos, which have lens distortion. The harness paired it with the straightened photos, which are even a different size (about 6200 × 4130 instead of 6048 × 4032). The original code crashed on the very first photo. We now re-map the depth through the lens model, the same way MapAnything's own ETH3D code does.

Three test scenes were labelled as practice scenes

When only some scenes were prepared, the code picked "practice" scenes from that subset instead of the fixed list. Three test scenes got the practice label. No model ever ran on them; we fixed the rule, added a test and rebuilt them.
