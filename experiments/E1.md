# E1 — Do wrong hints make MapAnything worse than no hints?

**Question:** when MapAnything is given wrong hints (camera positions, lens settings, depth), does it end up *worse than images only*? Which kinds of error cause it? Does one bad hint damage the good views? Does the model notice?

**Why it comes first:** E2 (why) and E3 (detect and fix) only make sense if E1 finds a real, realistic failure. E1 alone, done carefully, is a workshop-level finding.

**Time (A100, estimate):** about 2–2.5 h wall-clock.
- About 60 min: Claude Code writes the new hint-damage code and tests, with the VM off.
- About 5 min: GPU practice run on the dev scenes.
- About 30–50 min: GPU run on the eval scenes.
- About 15 min: tables and plots.

Replace these with the per-inference time measured in E0.

**Who does what:** [CC] = Claude Code, [YOU] = you run on the server.

## 2. Code to write [CC] (VM off)

All new damage functions go in `exp1/corrupt_geometry.py`, or a new `exp1/corrupt_inputs.py` for intrinsics and depth. Each gets:
- a config entry;
- a manifest entry that logs the exact damage per view;
- unit tests in `tests/` covering:
  - exact magnitudes;
  - determinism by seed;
  - factor = 1 or size = 0 giving exactly the clean input;
  - view-0 rules.

Extend `exp1/model_io.py` (still the only file that calls MapAnything) to pass:
- `depth_z` for selected views (requires intrinsics);
- `is_metric_scale` per view, as found in E0.

**New per-view logging (`per_view.csv`)** for every run and view: `view_idx`, `was_corrupted`, and the following fields. They feed the E1 signals and give E3 a free head start:
- `conf_mean`, `conf_median`: the model's own confidence for that view.
- `hint_rot_err`, `hint_trans_err`: how wrong the given hint was, against the truth.
- `pred_rot_err`, `pred_trans_err`: how wrong the model's output pose is, against the truth.
- **`absorption`** = `pred_err / hint_err`, for corrupted views only.
  - ≈ 1 means the model copied the bad hint (blind trust).
  - ≈ 0 means the model ignored it.
- `disagree_rgbonly_rot`, `disagree_rgbonly_dir`: how far the given hint is from the images-only prediction. This is the score behind Shubh's simple filter, now logged as a number.
- `view_pts_err`, `view_depth_absrel`: per-view errors, used for contamination.

**New per-run metrics:**
- `metric_scale_ratio` = predicted metric scale ÷ true scale (from `metric_scaling_factor` or the raw point cloud).
- Raw metric point error, with no rescaling. This is the main metric for scale-type damage, as decided.

## 3. The test grid (the full spectrum)

13 clips: 3 dev + 10 eval, 10 views each. "L" = the clip's scene size (median camera distance from the centroid). Every L value is also reported in meters per scene.

"Seeds" = 3 random directions per setting, for random-direction damage.

"+ctrl" = also run `drop_oracle` (ORACLE: removes exactly the damaged hints) and `filter_rgbcheck` (deployable simple filter).

### 3.1 Reference runs (no damage)

| Name | Hints | Purpose |
|---|---|---|
| `rgb_only` | none | floor |
| `rgb_K` | lens | floor + lens |
| `clean_pose` | lens + poses | ceiling |
| `clean_pose_noK` | poses only | lens effect |
| `zero_noise` | lens + poses through the damage code, size 0 | harness check |
| `rgb_K_depth2` | lens + true depth on views 3 and 7 | depth floor |
| `clean_pose_depth2` | lens + poses + true depth on views 3 and 7 | depth ceiling |

### 3.2 Sanity controls: these SHOULD be harmless

If any of these hurts, suspect a harness bug first.

| Name | What | Expected |
|---|---|---|
| `gauge_rigid` | same random rotation + shift applied to *all* poses, including view 0 | ≈ `clean_pose` |
| `scale_all_nonmetric_x1.5` | all translations × 1.5, but flagged non-metric | ≈ `clean_pose` on scale-aligned metrics |
| `scale_all_x1.0` | factor 1 | exactly `clean_pose` |

### 3.3 Family P: independent pose errors (each view wrong on its own)

| Name | Severity sweep | Seeds | Ctrl | Real-world cause |
|---|---|---|---|---|
| P1 `noise_rot` | all views, 0.5, 1, 2, 5° | 3 | – | jittery tracking |
| P2 `noise_trans` | all views, 0.5, 1, 2, 5% of L | 3 | – | jittery tracking |
| P3 `outlier_rot` | 1 view, 5, 15, 30, 90° | 3 | +ctrl | one bad compass reading / flipped orientation |
| P4 `outlier_trans_small` | 1 view, 0.1, 0.25, 0.5 L | 3 | +ctrl | small GPS glitch |
| P5 `outlier_trans_large` | 1 view, 1, 3, 10 L | 3 | +ctrl | GPS jump |
| P6 `outlier_frac` | 10, 20, 40% of views, each 15° + 0.25 L | 3 | +ctrl | bad stretch of sensor data |

### 3.4 Family C: correlated pose errors (errors agree with each other, the "agrees but wrong" case)

| Name | Severity sweep | Seeds | Ctrl | Real-world cause |
|---|---|---|---|---|
| C1 `scale_all` (metric) | all translations × 0.5, 0.67, 0.8, 1.25, 1.5, 2 | 1 | `filter_rgbcheck` | wrong units / scale drift |
| C2 `drift` | accumulated per-frame heading bias + per-frame scale growth, 3 severities (0.5°+1%, 1°+2%, 2°+4% per frame) | 3 | `filter_rgbcheck` | odometry drift |
| C3 `shared_heading_bias` | same orientation error on all non-reference cameras, 2, 5, 10° | 3 | `filter_rgbcheck` | compass / gravity misalignment |
| C4 `anchor_error` | view 0 (the reference) wrong by 15° or 0.25 L | 3 | – | bad first frame |

For family C, the oracle is "drop all poses" = `rgb_K`, which is already a reference run.

### 3.5 Family K: lens (intrinsics) errors

| Name | Severity sweep | Seeds | Real-world cause |
|---|---|---|---|
| K1 `focal_all` (with clean poses) | fx, fy × 0.8, 0.9, 1.1, 1.2 | 1 | wrong EXIF / calibration |
| K2 `focal_all_noposes` (vs `rgb_K`) | × 0.8, 0.9, 1.1, 1.2 | 1 | the same, with lens hints only |
| K3 `focal_one` | 1 view × 0.7 or 1.3 | 3 (view choice) | one photo with wrong metadata |
| K4 `principal_shift` | all views, cx and cy shifted by 5% or 10% of width | 1 | crop/resize metadata bug |

### 3.6 Family D: depth-hint errors (on views 3 and 7)

| Name | Severity sweep | Seeds | Real-world cause |
|---|---|---|---|
| D1 `depth_scale` (with poses, and without poses) | × 0.67, 1.5 on both depth views | 1 | depth sensor / mono-depth scale wrong |
| D2 `depth_noise` | 5%, 10% multiplicative per pixel | 3 | noisy sensor |
| D3 `depth_one_scale` | only view 3 × 1.5 | 1 | one bad depth map |

### 3.7 Family M: metric-flag errors

| Name | What | Real-world cause |
|---|---|---|
| M1 `metric_flag_off` | true poses, but flagged non-metric | user forgets the flag |

## 6. Signals and decision rules (frozen at `e1-prereg`)

"Realistic severity" = the low-to-middle settings of each sweep. Before the paper, each family's realistic range must be justified with sources: typical phone GPS error, VIO drift rates, EXIF focal error, depth-sensor scale error.

| Signal | Plain meaning | YES if (eval split) |
|---|---|---|
| **S1 Harm** | Wrong hints make it worse than no hints | `benefit_lost` > 1 for at least one family at realistic severity; ≥ 7/10 scenes worse than `rgb_only`; paired 95% CI excludes 0 |
| **S2 Spread** | One bad hint damages the good views | In P3–P6, uncorrupted views' error rises vs `clean_pose` on the same views by ≥ 20% relative; paired CI excludes 0 |
| **S3 Blind trust** | The model copies bad hints | Median `absorption` ≥ 0.5 for single-view outliers |
| **S4 Silent** | The model gives no warning | The model's own confidence separates corrupted from clean views poorly (AUROC ≤ 0.65) |
| **S5 Simple fix fails** | The easy filter isn't enough | `filter_rgbcheck` recovers < 50% of the `drop_oracle` gain on the S1 families, or cannot apply (correlated families) |
| **S6 Agrees-but-wrong** | Correlated errors hurt | Any C/K/D family shows S1, or `metric_scale_ratio` off by > 20% while the simple filter flags nothing |
| **S7 Break-even is realistic** | The failure happens at realistic error sizes | The severity at which `benefit_lost` crosses 1 lies inside the family's realistic range |

`benefit_lost` = (error with damaged hints − error with clean hints) ÷ (error images-only − error with clean hints). For lens and depth families, use the matching floor and ceiling, e.g. `rgb_K_depth2` / `clean_pose_depth2`.

**Primary metrics:**
- `pts_relerr_scale` (3D shape) and `rre_deg` (camera rotation) for all families;
- raw metric point error and `metric_scale_ratio` for families C1, D1, M1.

### Decision

| Outcome | Condition | What it means | Next |
|---|---|---|---|
| **Strong GO** | S1 + S5 + S7, and (S2 or S6) | Real, realistic, not trivially fixable → method paper path | E2 and E3 |
| **Weak GO** | S1 true, but S5 or S7 false | Real but easy to fix or only at extreme errors → analysis/workshop path | E2 only (cheap), then decide |
| **STOP** | S1 false for every family | Graceful degradation, matching VPGGT/WorldMirror → no problem to fix | Short negative-result note; pivot |

S3 and S4 don't decide GO alone, but they shape the story:
- blind trust + silent failure = the strongest motivation;
- a strong confidence signal = E3 is easier, but less novel.

**Early E3 read (free from the logs):** report the AUROC of `disagree_rgbonly_*` for flagging corrupted views.
- If ≥ 0.95 on every family, detection is easy, and E3 must target the correlated (family C/K/D) cases to be novel.

## Amendments (2026-10-27, Claude Code; frozen together with the grid at `e1-prereg`)

Interpretations needed to make the plan executable. They were fixed before any E1 model run.

1. **Commands.** The analysis is `python -m exp1.e1_analysis --run results/e1_<split> [--checks]` (writes `<run>/agg/`), not `exp1.aggregate`. Grid: `configs/e1_full.json` (65 conditions, 235 inferences per clip).
2. **Realistic range** (§6), written per family into the config: drop the single most severe setting of a sweep; for two-sided factor sweeps (`scale_all`, `focal_all*`), drop the two outermost; for 2-setting sweeps keep the milder one, or both when they are symmetric (`focal_one`, `depth_scale*`). Both `anchor_error` settings count as realistic.
3. **S1 and S7.** As written, S1 ("at realistic severity") would make S7 always true. So S1 is tested at **every** severity, and S7 = at least one S1-qualifying setting lies in the realistic range. That keeps the Weak GO row meaningful. "Worse than `rgb_only`" means worse than the family's **floor**: `rgb_only` for pose families, `clean_pose_noK` / `rgb_only` for lens families, `clean_pose` / `rgb_K` for depth families. "≥ 7/10 scenes" = ≥ 70% of clips.
4. **benefit_lost** = ratio of means over clips: (mean x − mean ceiling) / (mean floor − mean ceiling). CI = bootstrap over clips. Floors and ceilings are written per family in the config. Scale families also use `scale_err` = |ln `metric_scale_ratio`| as a primary metric.
5. **S2** uses per-view errors (`view_pts_err_scale`; `pred_rot_err` on non-reference views) of the uncorrupted views vs `clean_pose` on the same views, at realistic severities. The per-run `rre_deg` on a view subset also counts pairs that include the corrupted view, so it cannot show spread.
6. **S4** is the within-run AUROC (clean vs corrupted views of the same run) of the model's view confidence, pooled over P3–P6 and `focal_one`.
7. **S5** holds if, for at least one S1 setting, the filter recovers < 50% of the oracle gain, drops no pose, or does not apply (lens, depth, anchor and metric-flag families). Oracle: `drop_oracle`; for C1–C3, `rgb_K`.
8. **S6** = an S1 setting in a C, K or D family, or `metric_scale_ratio` more than 20% off the clean-pose ratio at a realistic setting while the filter drops no pose.
9. **Decision gap.** S1, S5 and S7 true but neither S2 nor S6 → **Weak GO** (the table does not cover this case).
10. **Sanity tolerances** (dev checks): `gauge_rigid` and `scale_all_nonmetric_x1.5` within 5% relative of `clean_pose` on `pts_relerr_scale` and `rre_deg`. `zero_noise` and `scale_all_x1.0` must equal `clean_pose` exactly (E0 noise floor = 0). Monotonicity: the most severe setting is ≥ 95% of the mildest. `drop_oracle` uncorrupted-view error ≤ 1.25 × `clean_pose` on the same views.
11. **Damage definitions.**
    - `drift`: the relative motions are re-integrated with a per-step heading bias about the camera's own y axis (tilted at random by up to ~17°, random sign) and step i's translation scaled by (1 + g)^i.
    - `gauge_rigid`: 30° + 1 L.
    - `principal_shift`: +x and +y.
    - `focal_one`: a random non-reference view.
    - `depth_noise`: kept ≥ 5% of the true depth.
    - Depth hints are the sparse ETH3D GT depth on views 3 and 7.
    - Lens and depth damage runs with clean poses unless the name says `noposes`.
12. **Upright relief clips** (§1): implemented in `datasets.py` (`rotate_upright`) with the same rotation as MapAnything's ETH3D converter, and tested against an analytic plane. The GT check passes on both rebuilt clips (worst 0.10%, `reports/e1_upright_check/`).
13. **Dev-check changes after the dev practice run** (before the freeze; `results/e1_dev/agg/dev_checks.md`):
    - The first dev check run had 3 FAILs. Two were bugs in my check code.
      - *Monotonicity* compared settings that are not stronger and weaker versions of the same damage: `anchor_error` (a 15° turn vs a 0.25 L shift), and ×0.67 vs ×1.5 or ×0.7 vs ×1.3 (opposite directions). Now each direction of damage is checked separately, with ≥ 2 settings.
      - *Absorption filled* counted control runs where the bad hint had been removed. Now only `control == none` is counted.
    - The third FAIL was the plan's own expectation. `scale_all_nonmetric_x1.5` differs from `clean_pose` by up to 148% (terrace `rre_deg` 0.55° vs 0.22°), but equals `metric_flag_off` **exactly** on all 3 dev clips (rel. diff 0). So the harness behaves as designed: the translation scale is invisible with the flag off. The gap to `clean_pose` is the effect of turning the metric flag off, which only gates the pose-scale feature (`reports/e0_interface.md` Q9). Family M1 measures exactly this.
    - The gating check is now "`scale_all_nonmetric_x1.5` == `metric_flag_off` exactly". The comparison with `clean_pose` is reported as INFO.
    - With these changes, all gating checks pass on the dev run.
    - **Approved by the user before the freeze** (2026-10-27).
14. **Minimum effect for S1** (user-approved before the freeze): the damaged run's mean error must also be ≥ 5% above the floor's mean. benefit_lost divides by how much the clean hint helped, so it explodes when that is small (dev: depth ×0.67 gave benefit_lost 98 on `rre_deg` from a 0.14° change). On the dev run this rule removed no setting, because the floors are themselves small. The report therefore always shows absolute and relative differences next to benefit_lost.
15. **Reported, not gating:** for every family given poses, the same comparison against `rgb_K` (photos + lens, poses dropped), the practical fallback ("would dropping the poses be better?").
16. **Extra outputs:** `agg/scene_lengths.csv` (L in metres per clip). Visual examples of the main damage types are made on the dev clip `dev__delivery_area__c0` with `scripts/e0_demo_recon.py`, which now applies the same damage as the runner. They are qualitative, not results.
